# Context

Implement FlowForgeIQ Signal Inbox Phase 3: consolidate the public communication experience under one user-facing “Inbox.”

Phase 1 and Phase 2 are complete.

Phase 1 established the Signal Inbox persistence, workflow, route/API foundation, and tests.

Phase 2 established revision-safe Gmail dispatch:
- AI drafts can be edited.
- Editing invalidates prior approval.
- Approval applies to the current draft revision.
- Gmail sending is protected by the current dispatch/idempotency flow.
- Existing Gmail reply behavior and Signal Inbox Gmail behavior have provider-focused regression coverage.

The public product currently has overlapping communication destinations:
- A standard Inbox destination in `NavSidebar.tsx`.
- A separate Signal Inbox entry/view in `Home.tsx`.
- Existing Signal Inbox UI and backend workflow implemented under the `signal-inbox` domain.

The product decision is:

> Inbox = handle communication.  
> Copilot Queue = review AI-recommended operational decisions.

Signal Inbox remains an internal/domain/API term only. Do not rename backend routes, schema fields, API types, proposal-source values, workflow-state values, or internal domain identifiers in this phase.

# Goal

Make **Inbox** the only user-facing navigation destination for communication work.

Inbox should cover:
- Incoming supplier/customer messages.
- Messages requiring assessment.
- AI drafts awaiting review.
- Approved replies ready to send.
- Failed sends requiring resolution.
- Sent and skipped communication history.

Copilot Queue should remain a separate product surface for operational decisions, including:
- Shipment escalation.
- Missing-document follow-up.
- Payment-related actions.
- Timing, margin, or risk warnings.
- Other AI-recommended operational actions that are not primarily communication handling.

# Implementation requirements

## 1. One public Inbox destination

Make the existing public Inbox destination render the existing Signal Inbox communication workflow.

Requirements:

- The public sidebar/navigation label must be `Inbox`.
- The Inbox destination must present the existing Signal Inbox functionality.
- Preserve current Signal Inbox list/detail behavior, filters, AI-draft editing, approval, send state, failed-send handling, retry behavior where supported, sent view, and skipped view.
- Page heading, visible navigation labels, breadcrumbs, document title if applicable, empty states, help text, and user-facing descriptions must say `Inbox`, not `Signal Inbox`.
- Do not duplicate `SignalInbox.tsx` into another large page just to rename it.
- Reuse, compose, or minimally rename existing components according to repository conventions.
- Do not expose internal words such as “signal,” “signal status,” or `signal_inbox` in normal user-facing copy.

## 2. Remove duplicate public navigation

Remove the extra user-facing Signal Inbox destination from primary navigation.

Requirements:

- Users must not see `Inbox` and `Signal Inbox` as peer navigation items.
- Keep one communication destination named `Inbox`.
- Preserve the existing sidebar hierarchy and visual design as much as possible.
- If Signal Inbox currently has an actionable-work badge/count, move it to the public Inbox item.
- Do not create a second badge for the same communication workload.
- Do not show a badge if the current API cannot provide an accurate, efficient count without new backend work.

For a badge, actionable work should include only the statuses that require attention, where currently available:

- `new`
- `draft_ready`
- `approved`
- `send_failed`

Do not count `sent` or `skipped`.

If an accurate count would require a new API endpoint, broad client-side loading, or a backend query redesign, do not build it in this phase. Preserve no badge and document the limitation.

## 3. Preserve legacy Signal Inbox access

Preserve backward compatibility for existing Signal Inbox links, bookmarks, and routes/state.

Requirements:

- Existing links, routes, active-view values, and state values that previously opened Signal Inbox must still reach the same communication workflow.
- Prefer a clean redirect or alias to the public Inbox destination.
- Do not redirect-loop.
- Preserve selected message, query parameters, filters, and other context when current routing patterns make that feasible.
- Do not break existing browser back/forward behavior.
- Existing external/internal links that use `signal-inbox` may remain supported technically but must render the public Inbox experience.
- Add focused routing/navigation tests for the legacy alias behavior.

## 4. Inbox information architecture

Use user-facing labels that describe the user’s work, not the internal state-machine implementation.

The intended Inbox views/filters are:

- `Needs review`
  - New or unassessed communication and drafts requiring human attention.
- `AI drafts`
  - Messages with an AI draft ready for editing/review/approval.
- `Ready to send`
  - Approved replies awaiting delivery.
- `Failed`
  - Send failures requiring review or an explicit retry.
- `Sent`
  - Completed outbound communication.
- `Skipped`
  - Intentionally dismissed communication.

Implementation guidance:

- Map these labels to existing `signal_status` values without changing backend state names.
- Do not force every filter if `SignalInbox.tsx` already has a clearer compact filter design.
- Default the Inbox to actionable work.
- Keep Sent and Skipped reachable, but do not include them in the default attention view.
- Preserve existing channel badges/filters, such as Gmail and future channels, where already supported.
- Avoid user-facing “Signal” terminology.

## 5. Clarify Copilot Queue

Keep Copilot Queue functionally separate and do not change its backend/API contracts.

Add concise explanatory copy, using existing visual, localization, and empty-state patterns:

> Review AI-recommended actions for shipments, documents, payments, and risk.

Requirements:

- Do not call Copilot Queue an Inbox.
- Do not frame it as a place to reply to customer or supplier messages.
- Do not remove or alter existing Copilot Queue items, sorting, filtering, or actions.
- Keep the change limited to product clarity, page header, supporting description, and/or empty-state guidance.
- Preserve all current behavior.

## 6. Design, accessibility, and responsiveness

- Reuse existing UI components, iconography, visual tokens, localization, and navigation patterns.
- Preserve responsive behavior.
- Ensure active navigation state is correct for Inbox, including legacy Signal Inbox aliases.
- Use accessible labels for navigation controls, status filters, and badge counts.
- Preserve current safe treatment of untrusted inbound message content.
- Do not make the page more monolithic; extract only small cohesive components if the current implementation needs it.
